# 「一箇所直すと他が壊れる」問題への対策

## 現状の課題
- バグを修正した際、予期せぬ場所で二次的な不具合（デグレード）が発生する。
- 修正の影響範囲が把握しきれず、デバッグがループに陥る。

## 解決のためのアプローチ

### 1. グローバル変数の削減と疎結合化
- 多くの関数から参照されるグローバル変数が原因であることが多い。
- 可能な限り、引数でデータを渡し、戻り値で結果を返す「純粋関数」に近い形にすることで、他への影響を遮断する。

### 2. 変更履歴の活用と AI による影響分析
- コードを大幅に変更する前に、現在の正常に動いているコードをバックアップ（または Git 管理）する。
- 修正案を適用する前に、AI に「この修正によって、他の `XXX` 関数や `YYY` 処理に悪影響が出る可能性はあるか？」と具体的に問いかける。

### 3. ステップ実行とログ出力の強化
- 修正箇所だけでなく、その前後のデータの流れを `console.log` で詳細に出力し、「なぜそこが変わったのか」を可視化する。

### 4. 共通ロジックの共通化
- 似たような処理が散在していると、一箇所直しても他が古いまま残り、不整合が起きる。
- 共通処理は一つのユーティリティ関数にまとめ、そこだけを直せば済むように設計する（DRY原則：Don't Repeat Yourself）。

## メンタルモデル：急がば回れ
「3時間のデバッグ」を避けるためには、最初の 30 分で「全体の影響を把握し、テスト用のダミーデータを用意する」といった、急がば回れの準備が最も効果的である。
